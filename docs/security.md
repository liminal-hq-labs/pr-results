# Security

> **Planned.** `pr-results` posts nothing yet: the command line does not call the publisher. Built and tested are the XML limits, the text rules, the `Safe` type and the trusted values in `pr-results-core`, the renderer in `pr-results-render`, and in `pr-results-github` the zip reader, the client that keeps the token off every other host, the pull request verification, the author-checked marker and the publish flow, against an in-memory GitHub and loopback servers. None of it has talked to the real GitHub API. This page states the design rules the tool must follow, so a product can prepare its CI now. Nothing here describes shipped behaviour. The rules themselves are normative in [SPEC.md](../SPEC.md#the-workflow_run-flow-and-security).

How `pr-results` must handle untrusted input, and why it is designed to run on fork pull requests. This page explains the model and says what to check.

## The threat

A pull request from a fork runs your tests with a read-only token, so it cannot post results. To post them, a second workflow has to run with write access after the tests finish. That second workflow reads files the first one produced, and the author of the pull request controls those files. The risks that follow:

- **Injection.** A test name, message or file path that holds Markdown or HTML changes how a comment renders: an image, a link, a mention, a closed `<details>` block or a broken code fence. A comment keeps its edit history, so content that was later escaped better stays visible.
- **Spoofing.** A forged event file names someone else's pull request, or a user posts a comment carrying the tool's hidden marker so the tool edits or trusts the wrong one.
- **Resource attacks.** A zip with an entity-bomb XML file, a symlink or `..` entry, a huge inflated entry, or a hundred thousand test cases.
- **Leaking.** Runner hostnames and environment values inside report files.
- **Workflow-command injection.** A test name or message written to a log, or into a `::error file=…::` annotation command, can carry `::` sequences that the runner executes as workflow commands, such as `::add-mask::`, `::set-output` or `::stop-commands::`.
- **Privilege.** Running or checking out code from the pull request in a workflow that holds a write token.

## The model

These are rules the tool must follow, not behaviour that exists today.

- **Two workflows.** The CI workflow is untrusted and read-only. The publisher is a `workflow_run` workflow that must run from the default branch with only the permissions listed in the specification: `actions: read`, `checks: write`, `pull-requests: write` and `contents: read`, with `permissions: {}` at workflow level.
- **No pull request code in the publisher.** It must never check out the pull request head. Its only checkout is a sparse checkout of `.github/` from the default branch, with `persist-credentials: false`. Nothing from an artefact may be run, sourced or used as a path outside the temporary directory.
- **One escaping type.** Every string from an input must reach the output through `Safe`, and test names, paths and failure text through its code forms, which GitHub does not scan for mentions. The renderer will have no function that accepts a plain string, so a missing escape is a type error rather than a review finding. Links are built only from parts the tool controls.
- **HTML lines hold only trusted words and numbers.** The renderer writes `<details>`, `<summary>` and `</details>` from literals and counts and never around a name, because Markdown inside a raw HTML line is not rendered and untrusted text there would be markup. A name goes on a Markdown line of its own, in a code span. The goldens are checked for this: outside code, the only HTML is those three tags and the hidden marker on the first line.
- **Fragments never join into a reference.** `Safe::text` breaks `GH-123` inside one fragment, but `Safe::concat` and `Safe::join` can build it from `GH` and `-123`, each safe alone. The renderer joins every line with `cat`, which puts a space between two fragments that would form a reference across the join, and a test fails if `Safe::concat` or `Safe::join` is called anywhere else in it. `Safe::text` is used only for the heading's title, which a literal colon separates from what follows.
- **Links are built, not passed.** `Safe::link` takes a `TrustedUrl`, which can be made only from the server, repository, commit hash and run id, each parsed with strict rules (a 40-digit lowercase hash, a host with no path or user). A forged comment marker is never read as ours: `Marker::parse` accepts exactly the line the tool writes.
- **Verified pull request.** The pull request must be found from the trusted event and the API, never from the uploaded event file alone. It must be open, at the run's head commit, from the run's head repository and into this one, and it is read again just before the comment is written. The event file (at most 1 MiB, one number read from it) only chooses among pull requests that already verified.
- **Author-checked marker.** The sticky comment is found by its marker and its author, and a user's comment with a forged marker is ignored. A later run's comment for the same commit is never overwritten by an earlier one that can see it, and the bot's duplicate comments for a key are removed so concurrent runs converge on one. Two limits are honest ones. GitHub has no conditional `PATCH` for a comment, so an older run that read before a newer one wrote can still overwrite it in a window of a few hundred milliseconds, and the stale text stands until the next run. And a re-list that lags a create can leave a duplicate until the next run removes it. The author check is the login alone (`github-actions[bot]`): the `[bot]` suffix cannot be registered by a person, so no user's comment passes it. A check run is ours only if its app is ours as well as its `external_id`.
- **Bounded memory.** An artefact is downloaded, inflated for the entries a section asks for, parsed and dropped before the next, the inflated bytes kept across the run are capped, and listing comments keeps 256 bytes of each, so neither a small zip that inflates enormously, many artefacts nor a hundred pages of large comments multiplies memory.
- **Bounded input.** DTDs are rejected, nesting is capped at 64, and archives are read by our own reader that takes the central directory only and stored and deflated entries only, and refuses zip64, encryption, split archives, absolute, `..`, backslash and drive-letter names, duplicates, symlinks and devices, offsets outside the archive and a bad CRC-32, with every length checked by `checked_*` arithmetic and inflating stopped at the declared size plus one byte. Total and per-entry sizes, file counts, suite counts and case counts are capped by `limits`, and so is what the report keeps in memory (64 MiB by default: all text, counted after invalid UTF-8 is replaced, plus a fixed overhead per piece of text, case and retry attempt), so neither a repeated value nor a flood of empty elements can multiply memory. Merging same-named suites is n log n, not quadratic.
- **Invisible characters are shown.** `Safe` spells out as `\u{…}` every format (`Cf`) and default-ignorable character, including the tag block that can carry hidden text, variation selectors, the soft hyphen and the fillers, as well as bidirectional and zero-width characters. The zero-width joiner and non-joiner are shown too, so a name that needs one reads with a visible code point.
- **Quiet output.** Hostnames, timestamps, properties and environment values must never be rendered.
- **No workflow-command injection.** Untrusted names and messages that reach a workflow log are escaped through the one `Safe` type: `%`, CR and LF always, and `:` and `,` as well inside command properties. Any untrusted log output is wrapped in `::stop-commands::<random token>` and resumed with the same token, so a `::` sequence in it is inert. Annotations are not written as `::error file=…::` commands: the renderer sends their title and message as plain text in a JSON body through the REST API, so workflow-command syntax is moot for them and matters only for log lines.
- **Annotations are not Markdown.** `Safe::plain_text` and `Safe::plain_block` drop controls, spell out invisible characters and do not map `@` and `#`, because GitHub documents an annotation as plain text that does not mention anyone or link an issue. That is documented behaviour and has not been verified here: the Q9 probe did not post annotations. Only `text`, `log_line` (which may be quoted in a comment) and the code forms are for Markdown.
- **Look-alike names.** A name can be made to look like another with characters that draw as blanks, so `Safe` spells out the `Zs` spaces other than U+0020 (such as the no-break space and the ideographic space) and the Braille blank U+2800, besides the invisible and format characters. Two names can still differ only by characters that look alike in some fonts, such as Cyrillic and Latin letters, so the renderer must show names in `Safe::code_span`, where they are at least set in monospace, and compares them by their exact text.
- **Debug output carries no text.** `Untrusted` prints its size and nothing else with `{:?}`, so raw report text cannot reach a log or an assertion message by formatting a struct. Nothing else in the model formats raw text.
- **Few secrets.** The token is `GITHUB_TOKEN` and nothing else. It is sent only to the GitHub API base: it is added in one function, to a URL made of the base and an `ApiPath` that cannot hold a host, and a `Link` header is followed only if it begins with the base exactly. The HTTP library follows no redirect. The artefact download's redirect to a presigned blob URL is fetched by a separate call with no `Authorization` header, which follows at most three more redirects, each to an `https://` URL on an allowed host (`*.blob.core.windows.net` and `*.githubusercontent.com` for github.com, the API host alone for another base, configurable for GitHub Enterprise Server), and refuses `http://` and any other host before sending anything. `Token` prints as a placeholder and has no `Display`; the command line masks it with `::add-mask::` before any request. Errors are fixed phrases that quote neither a response nor the library, which can echo a URL. It is never logged or written to disk. The `User-Agent` is `liminal-hq-pr-results/<version>` and carries no address of a person.
- **Writes are not repeated blindly.** A POST that failed with a 5xx or a dropped connection may have been applied, so it is repeated only after a read shows it was not (the check run by its `external_id`, the comment by its marker). A request that appends annotations is never repeated by the transport, because GitHub appends: the run's annotation count is read back first. One publish waits at most ten minutes in all to retry. Reads and idempotent writes back off 1, 2, 4 and 8 s, a rate limit is waited out only if it lifts within a minute, and writes are 500 ms apart.
- **Logs hold counts and fixed phrases.** The only names that reach a log are a section's title, through `Safe::log_line`, so the publisher needs no `::stop-commands::` wrapper.

## Pinning

Every action this repository uses is pinned by full commit SHA with its version in a comment, and container images are pinned by digest. A consumer that pins the composite action by SHA will also pin the exact binary, because `action.yml` at that commit will carry the binary's SHA-256. The publisher of this repository's own results must use the latest release pinned by SHA, never the pull request's build.

## What to check when you adopt it

Once the tool exists, check these in your own repository:

- The publisher workflow in your repository lists only the four permissions above.
- It triggers on `workflow_run` and does not check out `github.event.workflow_run.head_sha` or any pull request code.
- The `uses:` line is a full commit SHA with the version in a comment.
- Your configuration file lives on the default branch.

## Reporting a problem

Report a vulnerability privately through the repository's [security advisories](https://github.com/liminal-hq-labs/pr-results/security/advisories/new), not in a public issue.

## Not yet verified

Mentions and issue links (Q9) are verified in part (D43). The probe is `cargo run -p pr-results-render --example mention_probe`. It was posted as a comment in a throwaway private repository, as the owner's account because the token lacked the `workflow` scope, then edited with the same body and read back as rendered HTML. The raw control rows linked: `@user`, `@everyone`, `#1`, `GH-1` (read as an issue reference, not as the configured autolink) and the URLs. The fullwidth forms of `Safe::text`, `Safe::code_span`, `Safe::code_block` and the failure layout made no anchor at all but the trusted footer links. Not tested, and follow-ups for v0.2: notifications (a self-mention does not notify its author, and a bot author was not tried), `@team` mentions of a real team, cross-repository references to a real repository (the two controls for these were inconclusive), annotations, check-run text, the heading and table cells holding pipes. The probe has since gained the heading and the pipe rows, which have not been posted. A backslash escape is no defence either, since it is decoded before references are looked for. An HTML entity was rejected: GitHub's filters probably run on the rendered text, where the entity has decoded back to `@`, and the gh-aw project decodes entities before its own mention filtering for that reason. Code formatting is the documented workaround, so the renderer must put test names, paths and failure text in `Safe::code_span` or `Safe::code_block`, and use `Safe::text` only for the fixed words around them. The hostile-input fixtures that exercise each risk above are part of the [test plan](../SPEC.md#fork-safety-and-hostile-input-tests).
